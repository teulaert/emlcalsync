# Adversarial review — internal/{sync,store,mime,blob,calendar}

`go build ./...` and `go vet` on the five packages: clean.

## HIGH

**H1 · Provider rejection leaves the index permanently wrong (no rollback of the optimistic patch).** `internal/sync/outbox.go:105-141`. `Apply` writes the outbox row *and* `patchLocal` in one transaction, then calls the provider. On a non-offline rejection (400/403/404 — a label that does not exist, a message the account may not modify, a read-only calendar) the transaction is **not** rolled back and nothing re-reads the true state: the row keeps the optimistic flags/mailboxes, or the optimistically created `pending:` event stays in the index, or `OpEventDelete` leaves the event marked deleted although it still exists remotely. Because the provider never actually changed anything, no subsequent delta mentions that id, so the wrong state survives every later sync until a full `--full` reconcile. Repro: fake provider whose `SetFlags` returns a non-offline error; `Apply(OpFlags{Set:{Flagged}})` returns the error, then `GetMessage` shows `Flagged=true` while the provider has it false; every later `delta()` is a no-op. Fix: on the non-offline branch either re-read the affected ids from the provider (`FetchEnvelopes`/`GetEvent`) and re-apply, or record the pre-patch state in the op and restore it in the same transaction that marks the row failed.

**H2 · A hard-rejected write stays pending and is retried 10 times — including `send`.** `internal/sync/outbox.go:136-141` + `internal/store/state.go` (`MarkOutboxFailed` only does `attempts = attempts + 1, last_error = ?`; `done_at` stays NULL). The package doc (`internal/sync/engine.go:14-18`) and DESIGN §7.4 say a rejected write is "marked failed … rather than silently queued", but `ListOutbox(pending=true)` still returns it, so `emlcal status` reports it as pending and `RetryOutbox` re-executes it up to `maxOutboxAttempts`. For `OpSend` that means a message the provider rejected once (or accepted and then failed the response) is re-sent up to ten times. Repro: fake mail provider whose `Send` returns a permanent error; `Apply` returns it, then call `RetryOutbox` — `Attempted` is 1 each time, ten times over. Fix: distinguish permanent failure from offline — set `done_at` (or a `failed_at`/`give_up` column) on a non-offline rejection so retry skips it, and make `send` non-idempotent ops single-attempt.

**H3 · Reconcile resurrects a message but leaves it in no mailbox on any provider without `FetchEnvelopes` (i.e. JMAP/Fastmail).** `internal/sync/mail.go:762-766` + `800-810`, `internal/store/messages.go:471-511` / `525-556`. `MarkDeleted` deletes every `message_mailboxes` row; `MarkUndeleted` restores only `deleted_at` (its own comment defers membership to "the next UpsertMessage/UpdateMessageState"). In `reconcile`, a resurrected id lands in `existing`, not in `fetch`, so the only thing that could restore membership is `refreshEnvelopes` — which is guarded by `if ef, ok := r.mp.(envelopeFetcher)`. Only `internal/provider/gmail/fetch.go:44` implements it; the JMAP client does not. Result on Fastmail: the message is un-deleted, invisible in every mailbox listing (`mail list --mailbox inbox`, `--role inbox`), and stays that way — reconcile is exactly the recovery path after `ErrStateExpired`, so this is the state the tool lands in after a long offline period. The same gap leaves the flags/mailboxes of *every* existing message stale after a JMAP reconcile (the code logs a warning and moves on). Repro: `internal/sync/review_probe_test.go:TestReviewReconcileUndeleteLosesMailboxes` (uses the existing `bareMail` wrapper) — the message comes back with `MailboxRemotes = []` and the inbox listing is empty; the store half is the one failing assertion in `internal/store/review_probe_test.go:TestReviewFTSLifecycle`. Fix: reconcile should re-fetch resurrected ids through `fetchIndex` (they need their membership rebuilt anyway), or `MarkUndeleted` should take the envelope's mailbox list.

## MEDIUM

**M1 · Backfill never un-deletes a message it re-enumerates.** `internal/sync/mail.go:390-405`. `if exists && complete { continue }` skips the row entirely, so a message marked `deleted_at` locally that the provider still lists stays deleted and invisible. Reconcile handles this (`resurrect`), backfill does not. Reachable through the crash window in **M2** below, and through any `sync --full` on an account whose state is empty. Repro: `internal/sync/review_probe_test.go:TestReviewBackfillDoesNotUndelete`. Fix: in the `exists && complete` branch, collect ids whose local row has `deleted_at` set and pass them to `MarkUndeleted` (plus membership, per H3).

**M2 · Backfill finish is two transactions: a crash between them restarts the whole backfill with a *new* state token.** `internal/sync/mail.go:447-455`. `SetBackfill(finished)` and `SetState(S0)` are separate `Store` calls. A crash in between leaves `backfill_progress.finished_at` set and `sync_state.mail` empty, so `syncMail` (`mail.go:63-77`) falls through `bf != nil && !bf.Finished()` to `state == ""` and starts a brand-new backfill — re-enumerating the entire mailbox and capturing a *fresh* S0, which discards the original S0's replay window. Nothing is corrupted (existing rows are skipped) but hours of enumeration are repeated and any change that happened between the old S0 and the new one is only picked up because the enumeration re-lists it — deletions in that window are not. Fix: wrap both writes in one `st.Tx`.

**M3 · A message above `raw_max_size` is downloaded in full whenever the provider re-reports it as added and a row already exists.** `internal/sync/mail.go:550-564`. The size guard is `if oversize { if !exists { stub; continue } }` — when the row *does* exist (normally the stub written by an earlier pass) control falls through to `fetch = append(fetch, id)` and the whole message is pulled and archived, contradicting the `raw_max_size` policy (DESIGN §4) and flipping `raw_complete` to 1. On Gmail a label change surfaces as `messagesAdded` for that label, so this fires on ordinary activity on a large message. Repro: `internal/sync/review_probe_test.go:TestReviewOversizeRefetchedWhenRowExists`. Fix: when oversize, refresh flags/mailboxes (`UpdateMessageState`) instead of falling through to `fetch`.

**M4 · `mime.Build` emits header lines far over the RFC 5322 998-byte limit.** `internal/mime/build.go:198-216`. `writeHeader` folds only *between* space-separated tokens; a single token longer than the fold target is emitted whole. `Build`'s own doc says "no line longer than 998 bytes". A 2000-character subject with no spaces produces a 2009-byte `Subject:` line, and `Re: see https://…` with a 1500-character URL produces a 1521-byte continuation line — both are what a forwarded tracking URL or a machine-generated subject looks like, and strict MTAs reject them. Non-ASCII subjects are safe by accident (`QEncoding.Encode` splits into space-separated encoded words). Repro: `internal/mime/review_probe_test.go:TestReviewBuildLineLength`. Fix: hard-split any token that would exceed the limit (for `Subject`, force RFC 2047 encoding and let `QEncoding` chunk it; for other fields, fold at the limit).

**M5 · `StripQuotes` deletes real content in three ordinary shapes.** `internal/mime/quote.go`. Display-time only (`mail read`), so stored data is intact and `--full` recovers it, but the default view silently loses text. Confirmed by `internal/mime/review_probe_test.go:TestReviewStripQuotesFalsePositives`: (a) `quote.go:13` — a sentence that begins with "On" and ends in "wrote:" ("On the subject of the vendor contract, here is what their lawyer wrote:") is treated as an attribution and *everything after it* is cut; (b) `quote.go:55,184` — `reQuoted` drops every line starting with up to three spaces and `>`, so a pasted Python REPL transcript (`>>> import emlcal`) or a markdown block-quote the sender typed disappears; (c) `quote.go:196-207` — `cutSignature` fires on a bare `--` line, not just RFC 3676's `-- ` (with the trailing space), so a `--` used as a visual rule truncates the rest of the message. Fix: require the attribution line to be followed by quoted or indented material (or by an empty line then `>`); leave `>>>`-style lines alone; and require the trailing space on `--` (keep the bare form only when a signature-shaped block follows).

**M6 · A `message/rfc822` part with no `Content-Disposition` and no filename is not recorded as an attachment.** `internal/mime/parse.go:126-136`. `isAttachmentPart` needs `disposition == "attachment"`, or a filename on a non-text part, or an inline image with a Content-ID. A forwarded message attached as a bare `Content-Type: message/rfc822` part (common from Apple Mail and several webmail clients) matches none of them, so it is listed in `AllParts` but never in `Attachments` — `mail attachment list/get` cannot see it. Nothing is lost from the archive (the raw blob has it and `PartContent` can still reach the path), but it is invisible. Repro: `internal/mime/review_probe_test.go:TestReviewMessageRFC822Attachment` (the "bare" subtest). Fix: treat `message/rfc822` and `message/*` leaves as attachments.

**M7 · An empty mailbox list from a provider wipes every message's mailbox membership.** `internal/store/mailboxes.go:21-83` ("Pass 3: drop what the provider no longer has") + `internal/sync/mail.go:114-124`. `syncMailboxes` passes whatever `mp.Mailboxes(ctx)` returned straight to `ReplaceMailboxes`, which has no `len(mbs) == 0` guard: an empty (but non-error) response deletes every `mailboxes` row, and `message_mailboxes` cascades away with it. Every message stays in the index but is in no mailbox, so `mail list --mailbox/--role` returns nothing for the whole account until a reconcile — and on JMAP a reconcile does not restore membership either (see **H3**). `syncMailboxes` runs on the first delta of every pass, on every 20th delta, and whenever `noteUnknown` sees an unfamiliar id, so a single bad response is enough. Repro: `internal/store/review_probe_test.go:TestReviewEmptyMailboxListWipesMembership`. Fix: refuse to apply an empty list over a non-empty one (return an error, or keep the existing rows and log), the way the code already refuses to trust unknown mailbox ids.

## LOW

**L1 · Nesting deeper than `maxDepth = 24` loses the body entirely.** `internal/mime/parse.go:24,154`. Beyond the depth limit the multipart container itself is recorded as a leaf; because `keep` is `strings.HasPrefix(mt, "text/")` the container's bytes are drained and discarded, so `TextBody` comes back empty and the message is archived with nothing searchable. A depth-50 message parses in microseconds and never hangs — the limit does its job, it just fails closed on the text. Repro: `internal/mime/review_probe_test.go:TestReviewDeepNesting`. Fix: when the depth limit is hit, retain the container bytes as text so *something* is indexed.

**L2 · `blob.Put` reports `created = true` on the rename fallback even when it lost the race.** `internal/blob/blob.go:159-171`. Only reachable on a filesystem without hard links; the counter is cosmetic.

**L3 · The outbox retry timer map grows without bound.** `internal/sync/outbox.go:93-94, 653-663`. `retryAt` entries are only removed by `forgetAttempt` on success; rows abandoned at `maxOutboxAttempts` keep theirs for the daemon's lifetime. Bounded by the number of failed writes, so it is a leak in name only.

**L4 · `mailRun` relies on an undocumented "fn is called serially" contract.** `internal/sync/mail.go:284-346` guards `batch`/`seen` with a mutex but mutates `r.known`, `r.unresolved`, `r.roles` (through `noteUnknown` → `syncMailboxes` → `setMailboxes`) and `*done` from inside the `FetchRaw` callback with no lock. `provider.MailProvider.FetchRaw` (`internal/provider/provider.go:73-76`) only promises "calls fn for each one as it arrives (order not guaranteed)" — it never says serially. Both shipped providers do serialise (`gmail/fetch.go:22-32`, `jmap/mail.go:518,573-576` both hold a mutex around `fn`), so nothing races today; `internal/sync/review_probe_test.go:TestReviewFetchRawConcurrentCallback` drives a deliberately concurrent provider under `-race` and did not trip it in this run, but the window is narrow rather than absent. Fix: document the serial contract on the interface, or take `r`'s mutex in `noteUnknown` and make `done` atomic.

**L5 · A deletion discovered *after* the delta state was advanced can be lost on a crash.** `internal/sync/mail.go:588-606`. When there is nothing to update or remove, `setState` is attached to the final fetch batch; ids the provider announced as added but could not produce (`gone`) are only known once the fetch finishes, so their `MarkDeleted` runs in a transaction *after* the state moved. The code's comment says this is harmless because such an id was never indexed — true for a genuinely new message, but an `opAdded` for an id that already has a row (see **M3**) is a real deletion, and a crash in that gap drops it with no later delta to replay it. Fix: compute `hasTail` conservatively (never attach `setState` to the fetch when `fetch` is non-empty).

## Sound

- **`internal/blob`** — no findings beyond L2. tmp-file + `O_EXCL` + `Link` is genuinely atomic and race-exact, `Get` verifies the sha and rejects both a hash mismatch and undecompressable bytes, a permission-denied `Put` errors and leaves nothing behind, 32 concurrent `Put`s of the same content report `created` exactly once and leave `tmp/` empty, and empty content round-trips. `internal/blob/review_probe_test.go` passes clean under `-race`.
- **`internal/calendar`** — no findings. Verified against `internal/calendar/review_probe_test.go`: a daily 02:30 series across Europe/Amsterdam's spring-forward day keeps its 30-minute duration and normalises the non-existent 02:30 to 03:30 CEST while every other instance holds 02:30 wall clock; the autumn fall-back keeps 02:30 with strictly increasing instants; `UNTIL=…Z`, a zone-less `UNTIL` and the equivalent `COUNT` all yield the same 10 occurrences; multi-day all-day events straddling either window edge are returned and the half-open boundaries (`end == from`, `start == to`) are exact; an exception moved five months out disappears from its old slot and is attributed to the exception row, and a cancelled one just removes the instance; a busy block spanning midnight splits the range correctly, and working-hours windows never span a night and stay 09:00–18:00 wall clock on a clock-change day.
- **`internal/store` FTS5, search sanitisation, WAL and cascade** — no findings. `messages_ai/ad/au` keep the external-content index exact: rewriting `text_body` retires the old term and indexes the new one, delete/undelete round-trips without corrupting the index (`integrity-check` passes at every step — `TestReviewFTSLifecycle`'s only failing assertion is the H3 membership one), and `DeleteAccount` leaves zero FTS rows, threads, mailboxes, memberships and attachments while the other account stays searchable. Sixteen shapes of ordinary user input (`foo.bar`, `a:b`, an unbalanced quote, `*`, `NOT`, `OR`, `NEAR`, `(unclosed`, `C++`, `50%`, `who?`, `#tag`, `a/b`, `café`) either succeed or come back as `ErrBadQuery` — never a raw SQL error. Four reader goroutines running `ListMessages` + `Search` for two seconds against a writer committing 20-message transactions produced no `SQLITE_BUSY` and no index damage. `received_utc` round-trips as an instant, and `Since`/`Until` filter on that same instant.
- **Coalescing** (`internal/sync/mail.go:493-522`) matches DESIGN §7.2 as written (removal beats everything, add beats update, last update wins), and the "removed then added" ordering hazard is not reachable: Gmail only reports `Removed` for `messagesDeleted` (`gmail/changes.go:102-105,140-146`) and JMAP only for `destroyed` ids, neither of which is ever re-added under the same id.
- **Crash between `blob.Put` and `UpsertMessage`** is safe by construction: `mail.go:188-195` writes the blob first, so a crash leaves an orphan blob (collected by `GC` after the one-hour `orphanGrace`) and never a row pointing at a missing blob. `MarkEventDeleted` (`store/calendar.go:314-338`) deletes the event's `event_occurrences` rows itself and `ListOccurrences` filters `deleted_at IS NULL`, so a removed single event leaves no ghost in the agenda.
- **Resource use** — no unbounded loads found. `ListMessages`/`Search` project `messageCols`, which deliberately omits `text_body`; only the single-message getters and `GetThread` load bodies. `Reindex` pages 100 rows at a time, `attachMailboxes` chunks ids at 400, and every `QueryContext` in the reviewed packages closes its rows. The only unbounded goroutine is the per-account `pushLoop`, which is ctx-bound.
